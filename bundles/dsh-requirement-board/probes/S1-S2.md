## 3. S2 组合写入（`storage-sqlite` 行 + `storage-domain.routes`）

### 3.1 覆盖层方言：两条硬事实（原始实测）

- **新增行必须 `insert`**。`--patch` 顶层数组是 patch 列表；非 insert 且 id 不存在的条目走 `warn('patch: entry %C not found')` 后跳过（`vendor/include/src/index.ts:104-113`）。所以 `- id: storage-sqlite` 单独写会被静默跳过（OPTIMIZATION §2.4 的片段不能照抄）。
- **`- id: X` 的 `config` 是整体替换，不是深合并**（`vendor/include/src/index.ts:120-123`）。run 1 只写 `routes` 就炸掉整行：

### 3.3 依赖解析机制：为什么 `storage-sqlite` 必须在 `dependencies`

`node .artifacts/requirement-board/probes/s2-resolution.mjs` 直接调用 `createRuntimeResolution({installAnchor: apps/cli/package.json, profile: web})`：

**放 `devDependencies` 时（run 1/2 之前的状态）：**

```text

  installation @deepseek-ai/dsh-storage              -> ...\packages\bundle\base\node_modules\@deepseek-ai\dsh-storage
  installation @deepseek-ai/dsh-storage-domain       -> ...\packages\bundle\base\node_modules\@deepseek-ai\dsh-storage-domain
  installation @deepseek-ai/dsh-storage-json         -> ...\packages\bundle\base\node_modules\@deepseek-ai\dsh-storage-json
```

**放进 `dependencies` 后：**


原因：解析清单只跟 `dependencies + peerDependencies`（`packages/boot/app-boot/src/profile.ts:368`），且 profile 自身的 `node_modules` 里没有 `@deepseek-ai` 作用域目录（实测只有 `.pnpm` + 5 个 `link:` 插件符号链接）。`dsh-requirement-board` 是 profile bundles 里的一个 bundle 层，它的 `dependencies` 因此成为 profile-scope entry 的来源。

> 注：源码启动（tsx + tsconfig paths）会掩盖这一点——run 1 里 storage-sqlite 行就已加载。所以 `dependencies` 这条不是为了让源码启动「跑起来」，而是让**解析清单/构建启动**正确，并为阶段 0 的离线测试提供稳定解析。

### 3.6 S2 结论

**S2 可接受**，`dev.overlay.yml` 必须同时满足 §0 的四个硬条件。当前文件内容：

```yaml
- insert:
    - id: storage-sqlite
      name: "@deepseek-ai/dsh-storage-sqlite"
      config:
        path: "C:/code/deepseek-harness/.artifacts/requirement-board/dev-board.db"
        journalMode: wal
- id: storage-domain
  config:
    backend: json
    routes:
      requirement_board: sqlite
- id: requirement-board
  config:
    importLegacy: false
# TODO(stage A1): 四个自定义预设的 isolate 组（ROLE-DISPATCH §2.3），本阶段故意不写
```

`- id: requirement-board` 同样整体替换该行 config（丢失 `dataDir/defaultTemplateId/stallAfterHours/promptContext/promptMaxItems/http`）；这些字段的默认值与基础层取值逐一等价（`host/config.js` 的默认值相同），且 `importLegacy` 目前被 `resolveConfig` 忽略（未知键不校验），阶段 0 落地后生效。

### 3.7 Plan B（退回 json 后端）实测结论

**可行，且是运行时天然路径**：把 `routes` 键写错（或整条 storage-sqlite 行去掉、`routes` 删除）时，`requirement_board` 域自动走默认 `backend: json`，`open`/`put`/`get`/`close` 全部正常（§3.5 的 write 往返 `error: null`，json 文档结构完整）。回滚代价 = 改回覆盖层一行 + 重启 Host（无锁、无 schema 变更）。注意：json 后端的单元版本语义与 sqlite 不同（json 整单元存 `{unit:{name,version},global,tables}`；sqlite 在 `units` 表按单元精确版本戳），跨后端回退仍需阶段 0 的 export 反向导出，不能只改路由就指望数据自动迁移。

## 6. 遗留风险与对后续阶段的约束

1. **源码启动 vs 构建启动的解析差异**（§2.5）：源码启动下 `@deepseek-ai/*` 经 tsx tsconfig paths 解析到 `src/*.ts`；构建启动走解析条目的 `lib/index.js`。阶段 0 的离线测试（`node tests/domain.mjs`）走纯 Node → `lib/index.js`，因此**改动 storage 包源码后必须重新 `pnpm run build`（或至少确保 `packages/storage/*/lib/` 与源码一致）**，否则离线测试看到的是旧 lib。
2. **`dev-board.db` 被有意删除**：探针以 v1 写入会给 sqlite 单元打上 `version=1` 精确版本戳；storage-sqlite 对单元版本做**精确相等**校验（`packages/storage/storage-sqlite/src/index.ts:105`，`version-mismatch`），阶段 0 的 v2 描述符会打不开。所以取证后已删除 `dev-board.db{,-wal,-shm}`，阶段 0 在覆盖层指定路径上重新生成。若要人工复核库文件，重跑 §4 步骤 3 即可。
3. **运行中不可变更解析条目**：`ProfileRuntimeResolution.replace` 对已存在的 profile entry 换 `packageDir` 会抛「requires a process restart」（`resolver.ts:385-397`）。**不要在 Host 运行期间增删/改向 `node_modules` 或 `dependencies`**；3080 未受影响（探测后 pid 4636、StartTime 未变、HTTP 401）。
4. **run 2 使用默认 json 根**（`~/.dsh/storages`，与生产一致）打开其它域；对照 run 已把 json 根重定向进 `probes/`，并已删除含用户 workspace 数据的副本 `probes/s2-control-storages/`。临时实例未创建会话、未写 session 数据。
5. **`- id: requirement-board config` 整体替换**：阶段 0 若在插件自身 `cordis.patch.yml` 里已有完整 config，覆盖层只写 `importLegacy` 会把该行 config 收窄为单字段。当前默认值等价无副作用；阶段 0/G 合并时建议覆盖层只保留真正需要覆盖的键，或改为在插件行 config 里就地声明 `importLegacy`。
6. **`probes/` 全部是开发诊断物**，不属于产品包（`package.json` 的 `files` 未包含 `probes`）；阶段 R 归位 bundle 时不应带上，或明确保留为开发证据。
