## 一、目标与需求覆盖：完整，两处口径缺口

§1.1 的 17 行需求表与正文互指闭环，“做不到/不做”（§1.2）诚实划界（尤其“不承诺多进程安全”“不通知”）。缺口：

- **【低】§5.6**：`get` 返回 `lock`/`delegatedTo`/`executions`/`sync`/队列，但没带 §4.4 的 `claimable`/`advanceable`。模型“接之前先 `get`”（§7.2 第 13 条）恰恰最需要这两个派生值。建议 `get` 一并返回——§4.5 已保证单一公式，成本为零。
- **【低】§5.5 归属规则**：“无持锁会话的事件不落库、`syncSkipped`+1”——在 `requireLockForExecution` 默认关（§5.4）的前提下，非看板执行是**常态**而非竞态，计数会持续上涨且无解释。建议在 stats 命名或文档里注明“非看板执行不计入”，避免误判丢数据。

## 二、架构与技术选型：合理，契合现有栈，三处风险

选型判断全部成立：角色做成数据实体而非预设（规避了 2.4 已核实的“子会话无预设入参”平台事实）、存储走 `ctx.storage.domain`（接口与事件契约我已核验）、skill 与插件单向解耦。风险：

- **【高】§5.5 步骤 1——父会话获取子会话 id 的来源未闭环，且隐含未声明的部署前提**。方案写“id 从 `subagent/start` 事件取”——那是**插件**的 host 侧视角；父会话（模型）只能看工具回执。而工具回执三态（已核验 `tool-subagent/src/index.ts:529-560`）：`foreground` 阻塞到结束（无法中途 delegate）、`background`（**one-shot 默认**）只回 `jobId`（非会话 id）、只有 `continuable` 模式回 `subagentId: started.childId`。本机 `~/.dsh/profiles/web/cordis.yml:324` 恰好配了 `backgroundMode: continuable`，所以**在你的机器上流程成立**——但方案从未声明这个前提，换默认配置的部署直接不可用。同时步骤 4“按模板告诉子会话”存在时序矛盾：7.2 模板①含铸造出来的 `<roleId>`，而 roleId 在步骤 3 才存在，不可能出现在步骤 1 的初始 prompt 里。
  **修改建议**：① §1.2/§11 明确记录部署前提 `backgroundMode: 'continuable'`；② 步骤 1 改为“continuable 后台模式起子会话，**从工具回执拿 `subagentId`**”；③ 步骤 4 明确走 `send_message`（continuable 契约支持）在 delegate **之后**发送模板，或注明初始 prompt 为待命提示、roleId 由注入段承载；④ 7.2 模板①标注“roleId 来自看板注入段，不必手填”。
- **【中】§13.1 与阶段 0 自相矛盾**：§13.1 数据行说开发期覆盖层给“独立 `dataDir`（dev-board.json）”，但阶段 0 属于开发期且**移除 `dataDir`**，验收项还要求“dataDir 移除后旧配置明确失败”——阶段 0 落地当天 dev 覆盖层就把插件弄挂。且一次性导入条件“requirements 为空且旧 JSON 存在”会把生产数据 `~/.dsh/requirement-board/requirement-board.json`（已确认存在）导进开发库。
  **修改建议**：开发期隔离改为覆盖层给 `storage-sqlite` 一个**独立 path**（如 `.artifacts/…/dev-board.db`）+ `routes` 指向；旧 JSON 导入改为显式开关（如 `importLegacy`，默认只在生产 R 阶段开一次），或导入后在 global 记 `imported` 标记防重放。
- **【中】§11 S1（zod 解析）是全方案唯一无退路的未决点**。S2 失败有退路（json 后端），S1 失败则阶段 0 及 §4.1 整套存储设计搁浅且方案未写 Plan B。建议补一行：S1 不通过时的降级路径（domain 表单暂缓、`executionSync` 长期 false、写放大约束下沿用 JSON store + 手写校验），让“不可行”也有定义好的落点。

## 三、关键流程与数据设计：主体正确，两个高级流程缺陷 + 数据层小洞

- **【高】子会话“提前 claim”竞态（§5.5 vs §5.4 判定表第 3 条）**。已核验（`child-agent.ts:145`）子会话**继承父会话预设**；而 delegate 前置要求“父会话自己就能接”，意味着 `roleBefore` 必为 `''` 或父角色——**两种情况下子会话的继承角色同样满足判定表第 3 条**。子会话拿到初始提示立即 `claim`（7.2 第 ③ 条正是这么教的）→ delegate 落地时“未被别人上锁”不成立 → `conflict` → 临时角色永不铸造、`delegatedTo` 永不写入，派发机制在最常见执行路径下静默失效，且父会话无通道纠正。
  **修改建议**（建议 ①+② 并用）：① delegate 前置放宽为“未被**目标会话以外**的会话上锁”，锁持有者恰为目标子会话时幂等补写绑定（把竞态收编为正常路径）；② 派发模板把触发器从“消息说”改为“看板注入段出现 `Delegated to you` 再 claim”；③ 阶段 B 验收补一条“先 claim 后 delegate → 幂等收编”用例。顺带：prompt 组装应规定“存在待接指派时，`Claimable for you` 段降权或加‘先接指派’提示”，避免子会话用唯一那把锁去接了别的公共任务。
- **【高】“同一事务”措辞与平台写链能力不符（§3.3 表头、§5.2 delete、§5.5 revoke）**。已核验 `DomainImpl`（`storage-domain/src/domain.ts:148-201`）：单域**一条串行链，无跨行事务**。delegate（roles 行 + requirements 行）、delete（需求行 + N 个队列行 + N 条 `blocksOn` 引用）、`agent/disposed` 收尾，都是跨行序列——进程崩溃在中间会留下：孤儿 tmp 角色、指向已删任务的队列项（`reservedBy` 派生出幽灵预留）、未清的 `blocksOn`。§4.1 甚至把“无跨记录事务”当优点写，与 §3.3 的“同一事务”自相矛盾。
  **修改建议**：① 全文措辞统一为“同一写链（串行、非原子）”；② 所有派生（`reservedBy`/`children`/`blockedBy`）对不存在 id 做防御性 join；③ 插件启动时做一次清扫（sweep）：队列中不存在任务的项、`blocksOn` 悬挂 id、无 `boundTask` 的孤儿 tmp 角色；④ 阶段 A 验收加 sweep 用例。
- **【中】锁租约无续约（§5.2/§5.12）**。`lock.at` 只在 claim 时写；合法长任务超 8h 后 `expired → 可`，他人接管，原会话的下一步推进被 `forbidden`，两会话的执行单元混进同一任务。**修改建议**：持锁会话的任何成功写（executionSync 落库、checklist、transition）在同一次 `update` 里顺带刷新 `lock.at`——一行代码，建议直接采纳；补“活跃执行刷新租约”用例。
- **【中】面板“认领”语义未定义（§8 vs §2.5）**。面板 actor 是 `session:''`；claim 会把 `lock.session` 写成什么？若写 `''`，AI 侧 `lockAllows` 对该锁全部拒绝直到 8h 租约过期——面板一点“认领”就把任务锁死。**修改建议**：三选一——删掉面板“认领”按钮（人不受门禁约束，留“派发+清预留+推进”即可，推荐）；或面板认领以 `'human'` 名义持锁且不做过期、可随时释放；或面板从在线会话列表选人代持。
- **【中】`human` 未列入保留字校验（§2.3/§2.6）**。`ROLE_RE` 匹配 `human`，自定义预设可声明 `roleId: human` 劫持决策语义。一行修复：校验加 `!== 'human'`，`roles` 表 put 同拒。
- **【低】tmp 角色铸造无查重（§3.2）**：6 位随机撞 id 会改写他人 `boundTask`。建议直接用 `tmp-<任务id后缀>`（任务 id 全局唯一 → 天然不撞，且面板可读）。
- **【低】`requestedBy` 扫 history 首条 create（§4.4）**：500 上限裁掉后降级为 null。建议 create 时定格持久字段，history 扫描仅作迁移回填。
- **【低】`claimable` 公式含 `lock.session === me` 幂等分支（§4.5）**：自己持锁的任务同时出现在 §6 的 "Executing now" 与 "Claimable for you" 两段。§6 应明确组装规则：Claimable 段排除 `lock.session === me`。

## 四、性能 / 安全 / 可扩展性 / 可维护性

- **【中】SSE 读放大（§4.1 + §5.5）**：已核验**每次**链上写（含不推进 `rev` 的 executionSync）都 emit `domain/changed`，而 SSE 唯一来源就是它、面板收到即全量 refetch `/snapshot`。执行同步默认开，一个多话的 job（progress 文本变化）就能让所有打开的面板进入 refetch 风暴。§10 的写放大上界管住了写，没管住读。**修改建议**：SSE 层过滤——只对 `rev` 变化的写转发 `changed`（change 载荷里有新值，可判）；或 200–500ms 去抖合并（客户端本就全量刷新，无损）；执行单元表改为单任务低频刷新。§10 补一条“每次执行事件触发的 snapshot ≤1 次”用例。
- **【中】HTTP 无认证 × 新增高权限面板操作的组合暴露（§2.5/§5.6/§8）**：本机任意进程现在不止能改看板数据，还能以“人”名义清任意会话预留、推进决策、增删角色、派发/撤销。方案把“与现状一致”写进限制是对的，但**面确实扩大了**。建议把 OPTIMIZATION O7（路由 token）从 P2 提前为 R 的前置或紧随项。
- **【低】硬门槛拒绝消息（§5.4）**：`requireLockForExecution` 开启会拦所有无锁会话的子智能体/后台任务（含与看板无关的正常使用）。拒绝文案应指引“先 claim/queue，或请管理员关闭”。已默认关，诚实标注到位。
- **【低】token 预算（§5.6/§10）**：18+1 动作的测法建议从“改前改后量一次”升级为 snapshot pin 里的固定断言（首轮工具 schema 字符数上限），否则无回归守门。
- **可维护性（无级别，正面）**：§12 的单一装配点 + `dispatch.js` 收敛判定表/`claimable` 单一公式 + §10 的注入端口可测性改造，是对现有代码结构的实质改进；阶段 A 验收 20+ 用例建议按文件边界拆三个子阶段（锁与判定表 / 队列 / 角色解析），失败定位更快。

## 五、整体可行性与成立前提

**结论：方案整体可行，且成熟度高**——需求映射完整、平台证据全部属实、已吸收多轮评审（“评审发现的阻断项/后门”均有承接）、测试与回滚设计可执行。建议先修 3 个高级问题再进入阶段 A 开工。

5. 面板/HTTP 无认证的风险敞口在“本机单用户”语境下可接受（面已扩大，建议 token 提前）；
