# 看板任务：建、接、派

这份 skill 只讲**规范**：什么时候建、建成什么样、怎么接、怎么排队、怎么派、怎么协作、怎么收尾，以及每条的验收标准。动作名可以引用，但**参数与调用语法不在本 skill 里**——它们由工具自己的说明承载，工具是唯一权威。方向是单向的：skill 引用工具契约的公开动作与意图，插件不引用、不检测、不加载本 skill。

十五条覆盖：先查重、先查角色职能、一条任务一个交付物、必填四件事、先注册再跑、多任务先排队、派给子会话四件事、执行状态（看板自动同步）、门禁可选项、跨角色协作、要人拍板、不建的任务、认领礼仪、推进顺序、流程模板匹配（不符合就建模板）。

## 建之前

### 1. 先查重

建之前先用 `list` 动作看一遍：按可接筛选，再按关键字搜。**按可接筛选问的是"我这个会话现在能接什么"**（按我的角色过滤、排除别人持锁或预留的），不是全板"没人做"的清单。面板上的"可接手池"不过滤角色，那是给人的派发面，不是我能接的集合。

已经有人建了同题的任务，就不要另建一条；确需补充就把内容写进已有任务的描述，或作为子需求挂到它下面。看板只按任务 ID 认任务，**没有内容去重**——重复的活只能靠人挡住。

自检：新建前能说出"我查过，没有同题"，或者能说明为什么必须另建一条。

### 2. 先查角色职能

用 `requirement_role` 的 `list` 动作看现有角色的**职能**，按职能决定这条任务给谁：

- 有明确对应的角色 → 填上角色。
- 跨职能 / 谁都能做 → **留空**（留空 = 任意角色可接）。
- 不要按角色名猜职能；按职能字段判断。没写职能的角色无法按职能路由，会被标成缺职能——**兜底角色**（预设没有显式声明时，用预设 id 当角色）就是这种：它有角色 id，但没有职能。有**在跑会话**解析到、而库里没有记录的 id 会单列在"未登记"里，那也不等于"存在且有职能"。
- 角色本身只在面板里增删改，模型只能读；`human` 和 `tmp-` 打头是保留值，不能拿来当 AI 角色。

自检：角色取值能对上一个真实存在的职能，或者明确留空并知道原因。

## 建一条任务

### 3. 一条任务一个交付物

标题写成 `<动词> <宾语>（<交付物>）`，不超过 200 字，关键字前置。一条任务对应一个可验收的交付物；"顺便再做个 X"另建一条，不要塞进同一条。

自检：只读标题就知道要交什么。

### 4. 必填四件事

必填的是**标题、优先级、简述、描述**。简述是给人看的一句话门面，描述是给开工的人看的全文，两者分工不同：

- **简述**：一两句大白话说清要做什么、为什么值得做，不超过 300 字。不写实现方案、文件名、动作名、流程节点名，也不复述验收细节——那些属于描述。读简述的人多半不会往下读描述，所以简述自己就要能读懂。
- **描述**：写清三块——**做什么**（范围与边界，明确不碰什么）；**验收标准**（怎么算做完）；**交付到哪**（产物落在哪里、给谁看）。

面板把简述放在最显眼的位置、把描述收在下面的折叠区里，所以描述写得再细也不影响阅读；反过来，简述若写成描述的压缩版，就等于没有简述。

自检：把简述单独念给没看过这条任务的人听，他能说出"要做什么、为什么"；并且简述里没有实现细节、文件名或流程术语。

### 12. 不建的任务

下面这四类都不建任务：

- 一句话就能答的；
- 没有验收标准的；
- 角色不明的（先按第 2 条查清，或直接问）；
- 已经有人建过的重复项。

这类情况直接回答、先问清楚，或者并进已有任务。任务列表是执行队列，不是记事本。

## 接活与推进

### 5. 先注册再跑

动手前先用 `claim` 拿锁；**没有锁不要开始干活**。推进流程、勾检查项、改结构定义（角色、模板、父需求、前置依赖），以及阻塞、归档、删除，都要求持锁，无锁会被拒。默认下这只是看板对其自身操作面的强制：别的工具不拦你，所以更要自觉先上锁。运维可以打开"无锁不得执行"的开关，那时没有锁的会话调用起子智能体、后台任务或跑终端命令的工具会被直接拒绝（看板自己的工具仍然可用，所以拒绝从来不是死路）。

锁按任务 ID 互斥；**一个会话同时只持一把锁**，第二条会冲突。别人持的锁会拒你；**孤儿的锁（持有会话已结束）可以立即接管**，不必等租约；租约、续租与各种冲突码看 `claim` 动作自己的说明。你持锁期间的任何成功写都会顺带续租，所以长得合法的任务不会被静默易主。

`release` 是**异常离开时的显式放锁**（交接给别人、放弃、卡住了）：重复释放是一件本来就没有的状态，是成功的空操作，不报错、不写东西。正常走完不需要它——完成即自动放锁（见第 14 条）。

自检：在产出第一个交付物之前，这条任务的锁是我的。

### 6. 多任务先排队

手上有活时，把后续任务用 `queue` 排进**自己的**队列，做完手上的再接队头；不要试图同时开两条。排队是**软预留**：不取锁、不开始干活，也不改那条任务本身。已经被别人预留的任务，排队会当场被拒（预留先到先得）——等对方清掉或释放再排。队列有上界，满了会被拒，不会丢掉已有的预留。

预留**没有租约**：一个活着但卡住的会话会一直占住队内那条。会话结束时预留自动释放；人也可以在面板上清掉**任意会话**的预留。`unqueue` 清掉自己的预留，重复清是成功的空操作。面板不会替你认领，也不会替你排队——认领与排队只能由会话自己做。

自检：同一时刻我只持一把锁，其余都在我的队列里。

### 8. 执行状态：看板自动同步

看板会**观察**子智能体起止与后台任务事件，把它们折成执行单元，挂到**持有该任务锁的会话**名下（子会话自己拿了锁就挂它，否则挂派生它的父会话）。`get` / `list` 里因此有：

- `executions`：执行单元表（来源种类、标签、状态、进度、起止、`stale`）；超过上限会截断并标 `executionsTruncated`；
- `running`：还在跑的数量；
- `execRev`：**观察版本**，每次观察都动；业务 `rev` 只在任务本身被写时动——所以执行同步不会让你的 `expectedRev` 失效，也不代表任务被人编辑过；
- `sync`：观察的可信度（`enabled` / `gap` / `syncedAt` / `reason`）。

读它有三条规矩：

- **没有锁的会话的事件不落库**，只看不记：所以"看不到执行单元"不等于"没在干活"；
- `sync.gap` 表示**丢过观察**（可能滞后、可能有缺口），**不能当成"没有在执行"的证据**；`sync.enabled:false` 是同步被关掉，同样不是"没有执行单元"；
- 执行 `output` 不落库，重复的同一状态不重复写；接锁时会用后台任务注册表对账补齐。

所以：进度、阻塞、交接仍要写进任务**说明或流转说明**（`note`）；执行表是旁证，不替代说明。也不要为了"同步状态"重复建任务。

### 13. 认领礼仪

- 接之前先 `get` 一眼：锁在谁手里、是不是指名派给我的（返回里也会带上我自己的队列），以及两个只读给我的判断——`claimable`（我现在能不能接）和 `advanceable`（我持锁时能不能不 `force` 就推进）；
- 开工就 `claim`；完成即放锁（第 14 条），正常不需要手工 `release`；
- 做完先写 `note` 再 `advance`；
- 被门禁挡住（`gated`，或 `blockedBy` 非空）**不要 `force`**，除非在说明里写明越过的理由；被挡不影响"能不能接"，只说明推不动；
- 被拒时读理由：**写法本身不接受**（参数、形状、上界）和**写法没问题但当前状态/组合不允许**（例如队列已满、把任务派给自己）是两回事——前者换合法写法，后者先改状态、锁或预留，不要靠换写法绕过。

自检：每次推进都有说明；`force` 只出现在确有理由的那一次。

### 14. 推进顺序

在当前节点勾 `checklist` → 用 `transition` 推进到下个节点（`advance`）→ 最后用 `transition` 收尾（`complete`）。

- `complete` 在**同一次写**里放锁、释放该任务的预留，并收尾它的委托；回执只**提示**队头，不会替我接下一个。
- 走完最后一个节点的 `advance` 与 `complete` 一样算完成，同样放锁。
- 完成后要继续（包括 `reopen` 重开）必须**重新 `claim`**——锁已经放掉了。

自检：一条任务走完是"检查项 → 推进 → 完成"，没有跳步；完成的活要再做时我重新拿了锁。

## 派给子会话

### 7. 派给子会话：四件事 + 固定顺序

同角色的活可以派给子会话——**子会话继承我的角色**，所以它接不了别的角色的活。顺序不能变：

1. **起子会话**：用平台的子会话工具，以 **continuable 后台**模式起。这是部署前提：只有这个模式的工具回执才带**子会话 ID**；前台模式会阻塞到任务结束、one-shot 后台只回后台任务 ID，这两种情况都拿不到子会话 ID，派发链接不上（拿不到就要显式报错，不要静默换路）。
2. **`delegate`**：把这条任务指名派给那个子会话，并给出它负责的职能。**这一步之后**，这条任务才有属于它自己的角色 ID（`tmp-<任务id>` 形式的临时角色，只活到这条任务收尾）。
3. **`send_message` 发模板**：在 `delegate` **之后**，用 `send_message` 把这四件事发给子会话：

   - ① 你这条任务的角色 ID，看你自己 prompt 里的 `Delegated to you` 段——**看板注入段是权威来源**；我这条消息只作触发与确认，**不复述那个 ID**；
   - ② 任务 ID 与标题（我建的那条）已经注册给你；
   - ③ 开始前先按 `claim` 动作的说明拿锁，做完按 `complete` 动作的说明收尾；
   - ④ 验收标准与范围：不要碰什么、交付到哪。

**初始 prompt 只发待命提示**（因为角色 ID 在 `delegate` 之后才存在）："你即将接到一个看板任务。先不要自己认领任何任务；等我把角色 ID 与任务 ID 发给你，那时按 `claim` 的说明拿锁再开始。"——这样它不会用唯一那把锁去接别的公共任务。

派发的边界与例外：

- **目标必须是我自己的子会话**（平台按会话归属判断），面板上的人例外、可以派给任何会话。平台答不出归属时放行并留一次告警——那是组合异常，不是"谁都能派"的许可。
- **重复派发**同一条任务：先收尾旧委托，再建新绑定；**先 `claim` 后 `delegate`** 是幂等收编，只补记绑定、不报冲突（子会话继承我的角色，它本来就能先接）。
- **预留**：任务被第三方预留时派发被拒（先清预留）；预留者恰是目标会话时收编；**我自己预留的，派发成功后那条预留被释放**——活交出去了，不该再占着。
- **链式再派发**：临时角色的持有者可以把这条任务再派给**自己的**子会话（它通过绑定对这条任务有资格）。
- **撤销**：`revoke` 幂等，本来就没有委托也成功（回执标出没有变化），并释放目标会话在该任务上的预留。
- **收尾统一**：撤销、目标会话结束、重复派发、完成、归档、删除、挂载清理走同一套——删掉临时角色、清掉绑定、任务角色**回退到派发前的值**（永不会是 `tmp-*`）、锁放掉或标成孤儿。

**跨角色的活不要派给子会话**：它继承我的角色、接不了；应该注册一条任务给目标角色，等那个角色的会话来认领（见第 10 条）。

自检：子会话是从 continuable 回执拿到 ID 的；`delegate` 早于 `send_message`；我发的消息里没有复述角色 ID。派发模板与美术↔程序示例见 [dispatch.md](references/dispatch.md)。

## 跨角色与升级

### 9. 门禁是可选项

只有"必须先清掉某件事才能推进"时，才给任务加前置（`blocksOn`，最多 20 条，去重保序）；默认不加。**方向别写反**：`blocksOn` 是我声明依赖谁；`blockedBy` 是当前挡着我的那些未完成项（读时派生），`gated` 就是"我被挡着"。

- `advance` 与 `complete` 在 `blockedBy` 非空时**都会被拒**（并列出挡路的 ID）；`rollback` 不受门禁——往回走不是前进；`jump` 本来就要求 `force`。
- `force` 可以越过，**越过了哪些会被记进那一次的流转历史**；理由写进 `note`。
- **归档的挡路者不算完成**：它还在，要么 `force`，要么先把它重开。
- 判断的顺序是**先模板节点自己的前置，再跨需求门禁**；节点前置没满足时你看到的不是门禁错误。
- 抬高只给**拦路的那条**，封顶 `urgent`，**不落盘**（`priority` 字段不变），前置清掉自动回落；标 `[high↑]` 的只有被抬高者。`stats.criticalPath` 是"被抬高的条数"这个**计数**，不是被挡任务的集合。

`claimable` 与 `advanceable` 是两个口径：前者问"能不能接"，后者问"（持锁或面板）∧ 门禁已清 ∧ 节点前置已满足 ∧ 未完成未归档 ∧ 类型允许"能不能推。节点**自己的完成条件**不算进 `advanceable`——那是 `transition` 该报的，不是权限。

自检：要么没有前置，要么每个前置都对应一条"必须先做完"的活。

### 10. 跨角色协作

跨角色不要派子会话，用**需求图**表达：父需求 + 各自角色的子需求（挂父需求，读回 `children`）+ 前置依赖（等谁）。跨角色的建议也走"建一条给那个角色"这条路，让它的会话来认领。

两条结构规则：任务不能挂成自己的父需求、父子不能成环、前置不能自指或成环（两张图分别检，都会被拒）；删除一条任务会在收尾时把它从别人的前置与父需求里解绑（每处解绑各留一条历史，回执列出 `unbound`），并清掉队列预留——不会留下指向已删任务的悬空引用。

自检：跨角色的等待关系都落在需求上（前置依赖），不落在私下的消息里。

### 11. 要人拍板

需要人决定的事，建成**决策类需求**，描述里写清**选项 / 各自代价 / 默认建议**，并把正在等它的任务挂成它的前置。

决策类需求**只能由人在面板推进**：AI 会话对它的认领、流程推进、归档、删除、派发、排队**全部被拒**；`update` 也只准改标题、描述、优先级、标签、所属会话——不能改类型（**类型创建后不可变**，不能把决策类改成普通任务再认领）、角色、前置或父需求。读它是开放的，谁都能看到在等什么。

人可以把决策**派发**给某个会话（把问题与上下文交给它），但它在可接判定里**永远接不了**——收到决策类的指派时，读题、补上下文、等人推进，不要 `claim`。

自检：决策需求描述里能直接读出选项、代价与建议。

## 流程模板

### 15. 流程模板要匹配需求本身的流程

看板的一条需求就是一个流程实例：节点序列、节点前置（`dependsOn`）、检查项，以及 `advance` 的推进判定（当前节点算不算完成、下一个是谁），全部来自它绑定的模板——`complete` 是收尾动作，不看这些完成条件，只受跨需求门禁约束。所以**建需求之前先确认模板对得上这条活真实的推进方式**——默认模板在那里，不等于它可以随便用：`templateId` 省略时会**静默**绑到部署配置的默认模板。

- 先用 `flow_template` 的 `list` 动作读现有模板（id、描述、节点序列与各节点的完成条件），按**这条活真实的生命周期**挑：节点顺序、谁等谁、每步怎么算完成都能对上，才用它的 `templateId`。
- 一个都对不上（新的交付物类型、只有这条活才有的阶段、顺序与门禁都不同）→ **先建模板再建需求**：用 `flow_template` 的 `create` 动作把节点写成这条活真实的步骤（节点 id 稳定、`dependsOn` 串成链、需要别人照着判完成的节点写成 checklist），拿到新 id 后作为 `templateId` 建需求。
- 模板是**整个看板共享**的，不是某条需求私有的：名称与描述要写清"这条流程适用什么活"，同类活以后复用。内置的标准模板不能删；删除仍被占用的模板要 `force`，那些需求会被回退到默认模板。
- 模板不是只能建和删：要改进现有流程用 `revise` **追加一个版本**（存量需求一行不动，别为一个小改动去新建模板），需要换版的需求再用 `migrate` 迁到新版本（不指名 `requirementIds` 就是"全部钉在旧版的"，要 `force`）。另有 `archive`（`archive:false` 恢复）、`clone`（改内置流程的正路）、`delete`（按 `force` 把受影响需求改绑到默认模板并在需求侧写历史）；`prune`（裁剪历史版本）只在面板、不在工具面。
- 绑错模板不会在创建时报错，代价在后面显现：模板的节点前置与活的实际顺序对不上时推进报 `dependency-not-met`，检查项与交付物无关，推进顺序也与实际工作错位。事后改绑走 `update` 的 `templateId`（要锁），换模板会按新模板重算节点状态并留一条 `retemplate` 历史——能一次挑对就不要返工。

自检：`templateId` 指着的模板，节点序列与这条活真实的"下一步做什么"一致；不一致时，是我先建了匹配的模板再建需求，并说得出它为什么匹配。
