# 派发模板与协作示例

这份文件是 [SKILL.md](../SKILL.md) 第 7 条的展开：**同角色内**怎么把任务派给子会话、**跨角色**怎么协作。规范以 SKILL.md 为准，本文件只给可照抄的消息与流程；参数与调用语法仍以工具自身说明为准。**派发与撤销是同一个动作的两半**：撤销、重复派发、目标会话结束、完成、归档、删除、挂载清理都走同一套收尾。

## 0. 派发前必须成立的前提

- **子会话继承父会话的角色**，没有入参可以改它的角色——所以同角色的活才能派子会话，跨角色的活派不了。
- **必须能拿到子会话 ID**：起子会话时用 continuable 后台模式，工具回执里才有子会话 ID；前台模式会阻塞到任务结束，one-shot 后台只回后台任务 ID。拿不到子会话 ID 就**显式报错**，不要拿别的 id 猜。
- **目标必须是调用方自己的子会话**：平台按会话归属判断，不是自己的子会话会被拒；**面板上的人例外**，可以派给任何会话。平台答不出归属时（注册表拿不到）放行并留一次告警——那是可见的降级，不是"谁都能派"的许可。
- **派发方必须自己就能接这条任务**（任务不限角色，或角色就是我的角色），并且是这条任务的创建者、负责人或成员之一；不能把任务派给自己（自己做就直接 `claim`）。
- **锁与预留的三种关系**：
  - 锁在**目标会话**手里 → 幂等收编，只补记绑定，不报冲突（子会话继承我的角色，它本来就能先接）；
  - 锁在**第三方**会话手里 → 被拒，先按 `claim` 的说明处理（等租约、等对方结束、等孤儿锁可接管），不要硬来；
  - 预留：被**第三方**预留 → 派发被拒（先清预留）；预留者恰是**目标会话** → 收编；**我自己**预留的那条 → 派发成功后释放。

## 1. 固定顺序：起子会话 → `delegate` → `send_message`

| 步 | 谁 | 做什么 |
|---|---|---|
| 1 | 派发方 | 用平台子会话工具以 **continuable 后台**模式起子会话，从回执取**子会话 ID** |
| 2 | 派发方 | 用 `delegate` 把这条任务指名派给那个子会话，并给出它负责的职能——**这一步之后**任务才有自己的临时角色（`tmp-<任务id>`） |
| 3 | 派发方 | 用 `send_message` 发下面的四件事模板（`delegate` 之后才发，因为角色 ID 这时才存在） |

顺序不能换：初始 prompt 先发待命提示，引用角色 ID 的那句话必须在 `delegate` 之后才发得出去。

重复派发同一条任务时，**先收尾旧委托再建新绑定**；链式再派发是允许的——临时角色的持有者可以把这条任务再派给**自己的**子会话。

## 2. 初始 prompt（唯一在 `delegate` 之前发的待命提示）

```text
你即将接到一个看板任务。先不要自己认领任何任务；等我把角色 ID 与任务 ID 发给你，
那时按 claim 的说明拿锁再开始。
```

作用：子会话的任务还没派好之前，不让它用**唯一那把锁**去接别的公共任务。

## 3. 派发消息模板（`delegate` 之后发出，四件事）

```text
① 你这条任务的角色 ID，看你自己 prompt 里的 "Delegated to you" 段——那是权威来源，
   我在这里不重复它。
② 任务 <任务ID>（<标题>）已经注册给你。
③ 开始前先按 claim 动作的说明拿锁；做完按 complete 动作的说明收尾。
④ 范围与验收：<不要碰什么>；<交付到哪>；<怎么算做完>。
```

两条纪律：

- **角色 ID 的权威来源是看板注入段**（`Delegated to you`），派发方的消息只作触发与确认，**不复述铸造出来的那个 ID**；也不要在消息里另起一个角色名。
- 第 ④ 条要能独立成立：子会话看不到你和别人的上下文，范围、交付位置、验收标准都写进这条任务和这条消息里。

## 4. 子会话侧看到什么

子会话自己的 prompt 里有 `Delegated to you` 段，含这条任务、临时角色 ID 和"开始前先接"的措辞；存在这个段时，公共任务段会降权，提示它先接指派。它按 `claim` 的说明拿锁，执行，推进，最后 `complete` 收尾。

收尾是自动的：完成、归档、删除、撤销、目标会话结束，都会删掉临时角色、清掉绑定、把任务角色**回退到派发前的值**（永不会是 `tmp-*`），并放掉或标孤儿它的锁。目标会话在该任务上的预留也会随绑定结束被释放；撤销或重复派发时，结算前先放掉的是**被撤销那个会话**的预留。派发方不需要手工清理。

**决策类例外**：决策需求会被人从面板派发给某个会话——那是把**问题与上下文**交给它，不是交给它执行。派发后它出现在该会话的 `Delegated to you` 段里，但**永远接不了**（可接判定要求普通任务）。收到决策类的指派时：读题、补上下文、等人在面板推进，不要 `claim`。AI 会话自己也不能派发决策类。

**被指派 ≠ 推得动**：这条任务如果还挂着未完成的前置（`gated` / `blockedBy` 非空），子会话**能接，但 `advance` 与 `complete` 会被拒**。越门禁不是它的判断范围——等前置清掉，或让派发方处理，**不要自己 `force`**。派发前先 `get` 一眼：带未完成前置的任务，先想清楚是不是该等。

## 5. 示例：美术 ↔ 程序

> 下面用 `art`（美术）和 `code`（程序）当**示例角色 id**，用于说明写法；本机当前的角色声明见 [roles.md](roles.md)。

场景：要让角色"霜"上线，需要美术出立绘、程序接动画状态机。

### 5.1 同角色内部 → 派子会话

美术会话手上有一条"绘制霜的角色立绘（PNG 立绘）"，还需要一张同角色的切图。这是同角色的活，可以派给**自己的**子会话：

1. 以 continuable 后台起子会话，拿到子会话 ID；
2. `delegate` 这条切图任务给那个子会话，给出"切图"的职能；
3. `send_message` 发第 3 节的四件事模板，其中第 ④ 条写成："只切这一版立绘，不要改动原图；交付 4 张部件 PNG 到美术资源目录；验收标准 = 部件不重叠、命名符合规范、透明背景。"

子会话拿到锁后开工，完成后自动放行、自动收尾。若子会话抢先 `claim` 了这条任务，派发照样成立（幂等收编）。

### 5.2 跨角色 → 建需求，不派子会话

程序要做的动画状态机不能派给美术的子会话（子会话继承美术的角色，接不了程序的活）。改成需求图：

1. 先建或找父需求："角色「霜」上线（角色包）"；
2. 给美术建子需求："绘制霜的角色立绘（PNG 立绘）"，挂到父需求下；
3. 给程序建子需求："实现霜的技能动画状态机（可跑的状态机）"，同样挂到父需求下，并给它加**前置依赖**指向立绘那条——资源没到，程序那条虽然能被认领，但推不动；
4. 美术那条完成后，程序角色的会话就能推进它了。美术角色不需要写任何"通知程序"的消息：等待关系已经落在需求上。

要点：跨角色的等待关系**只表达在需求的前置依赖上**，不要靠私聊或"记得跟程序说一声"。前置挡住时**不要 `force`**，除非写明理由。拦路的立绘那条会被自动抬高优先级，不要手工给它加急。

### 5.3 跨角色建议同样走建需求

"要不要加个跳劈动作"这种跨角色的建议，也建一条给对应角色的任务（或建决策类需求请人拍板），不要只在消息里提。

## 6. 撤销派发与异常长什么样

- **撤销派发**：`revoke` 与派发是同一个动作的两半，**幂等**——本来就没有委托时也成功，回执明确标出没有变化（`changed: false`）。撤销会释放**被撤销那个会话**在该任务上的预留，并走与其它收尾完全相同的结算。
- **重复派发**：先收尾旧委托再建新绑定；不允许两个临时角色指向同一条任务（临时角色按任务 id 命名，一条任务只有一个）。
- **目标会话结束**：临时角色与绑定被结算，任务回到可接池；它持有的锁标为**孤儿**，**可以立即接管**（不必等租约）。挂载时的清理会扫掉上次中断留下的同类残渣；注册表拿不到时会降级为具名上报，不静默跳过。
- **拿不到子会话 ID**：说明起子会话的模式不对（前台或 one-shot 后台），派发链不可用——显式失败，不要退化成"把任务留在手里自己做"而不说。
- **派发被拒**：常见原因是目标不是调用方自己的子会话、调用方自己接不了这条任务或不是创建者/负责人/成员、任务被第三方预留、锁在目标会话以外的会话手里、任务已经是决策类（AI 侧）、或任务已结束。按拒绝理由先修正归属、锁或预留，再重试；不要绕过。
