# 知识库整体设计评估与优化建议

> 评估对象：[[DESIGN]] 与已落地的三块实现——host 引擎与 Remote 网关（packages/host/kb）、agent 工具（knowledge-base preset 的 kb.plugin.mjs）、GUI 面板（packages/client/ui-kb）。
> 参考输入：[[2026-08-15-codebase-mcp-适用性评估]] 的结论（不集成 codebase MCP；借鉴其增量索引、分块、混合检索模式）。

## 1. 结论摘要

设计方向正确：纯文件存储、状态由路径推导、双通道（GUI/agent）、2-gram 免分词，都是对的。主要问题在**实现与设计之间的系统性漂移**：

1. **双引擎实现**：同一知识库存在 host 与 preset 两套独立引擎，已产生 7 处可观察的行为不一致（§3.1）。
2. **检索能力未兑现**：DESIGN 承诺的相关度排序、命中高亮、字段语法、自动引用注入、批量确认、剪藏护栏多数未落地（§3.2）。
3. **索引维护粗糙**：面板每次打开、agent 每 10 秒、每次写库都是全量重扫 + 全量重写 index.json——codebase MCP 评估中「增量索引」建议的直接落点（§3.3）。

所有优化建议均与现有架构兼容，无颠覆性改动；按 P0（一致性）/P1（检索与索引）/P2（体验与远期）共 15 项列于 §4。

## 2. 现状盘点

| 层 | 实现 | 状态 |
|---|---|---|
| 引擎 | packages/host/kb KbEngine：2-gram 倒排、frontmatter 解析、路径推导状态、expectVersion 乐观锁、回收站 + 30 天清扫 | 进程内单实例、惰性初始化、经 fs 沙箱读写 |
| Remote/网关 | kb.list / search / get / saveDoc / createDoc / moveDoc / deleteDoc / trash / restoreDoc / purgeDoc / refresh 等 18 个方法 + `/dsh-kb` 图片路由 | 面板数据面；启动即清扫回收站、每 24h 定时 |
| agent 工具 | knowledge-base preset 的 kb.plugin.mjs：15 个 kb_* 工具 + 提示词段 | import-free 自含引擎副本（与 host 各写各的 `_meta/index.json`） |
| 面板 | packages/client/ui-kb 三栏工作区 | 打开时调用 kb.refresh 全量重扫；编辑走 host 引擎 |

索引事实：`_meta/index.json` schemaVersion 3，保存 title/tags/aliases/summary/source/created/updated/pinned/status/links；`images.json`、`trash.json` 为辅助注册表。当前库约 5 篇活跃文档，处于个人量级——以下问题在量级变大前修复成本最低。

## 3. 核心发现

### 3.1 双实现漂移（P0，最高优先）

host 引擎与 preset 副本是两份独立代码，已确认 7 处偏差：

| # | 偏差 | 证据 | 后果 |
|---|---|---|---|
| 1 | `01-inbox` 状态不一致 | host 的 INBOX_DIRS 含 01-inbox；preset 的 statusOf 只认 `00-inbox/` 与 `90-归档/` | 同一文档 GUI 显示 inbox、agent 判定 filed |
| 2 | archiveDir 配置不一致 | host 支持 `archiveDir` 配置；preset 硬编码 `90-归档`（statusOf、KB_DIRS、kb_archive 全是） | 修改配置后 agent 通道仍按旧目录归档 |
| 3 | images.json 格式冲突 | preset 的 kb_images 写数组 `[{path, name, referenced}]`；host 的 imageTarget 按对象 `Object.keys()` 读、resolve 又按数组 `.find()` 读 | host 按文件名回退查找图片失效（404） |
| 4 | kb_update 重复 `updated:` 键 | preset 在渲染循环之后再 push 一行 `updated:` | 落盘 frontmatter 出现两个 updated 键（解析取后者，文件脏，外部工具不兼容） |
| 5 | 排序不一致 | host 排序 pinned 置顶；preset 仅按 updated | 同一查询两个通道结果顺序不同 |
| 6 | index.json 双写竞争 | 两侧各自持有内存索引，写库后各自全量重写 index.json | agent 新建的文档可被 GUI 通道的下一次写库从 index.json 抹掉（磁盘文件仍在，需 refresh 恢复） |
| 7 | refresh 行为不一致 | host 的 refresh 重扫并重写 index.json；preset 的 refreshIndex 只重扫不写 | 刷新后两通道的 index.json 可能不一致 |

根因即 README 已知限制「Index duplication with the preset」：preset 因 ESM 解析器看不到 harness 包而被迫 import-free 自拷贝，两份实现必然漂移。**建议**：host 侧把引擎发布为服务（KbGateway 在 Remote 之外 provide 一个 `kb` service），preset 插件经 `ctx.get('kb')` 消费同一实例，工具只剩参数映射——一次性消除 #1–#7。若后续 preset 可引用包，再把工具收敛为 `@deepseek-ai/dsh-tool-kb`。

### 3.2 检索能力与设计承诺的差距（P1）

| DESIGN 承诺 | 现状 |
|---|---|
| §4.3 相关度排序 | 只有时间排序（+pinned），无词频/字段加权 |
| §4.3 命中高亮 | 未实现（wire 类型无高亮字段） |
| §4.3 字段语法 `tag:` / `path:` / `status:` / `title:` | preset 实现 tag/path/status（正则剥除后 AND）；GUI（host search）完全无字段语法；`title:` 两侧都没有 |
| §4.3 单字符查询 | 无 2-gram 直接返回空（中文单字不可搜） |
| §4.3② AI 引用式检索自动注入 | 未实现：无自动预检索、无 topK/bodyLimit 注入预算、无引用标注 |
| §4.2 批量操作断路器 | 未实现：kb_import 可任意批量导入；kb_archive 默认 dry-run 但无确认门 |
| §4.1 URL 剪藏护栏 | 仅 http(s) 正则 + 正文 20k 字符截断；超时/重试/SSRF 无显式护栏参数 |
| §4.10 注入遥测 | 未实现（命中率与 token 消耗） |
| §3.4 expectVersion 冲突返回 | `conflict` 字段恒为 false：fs 的 `replaceIfVersion` 版本不匹配抛 `FS_STALE_VERSION` 异常冒泡，协议字段是死代码（写入仍被安全拒绝） |

### 3.3 索引维护（P1，参考 codebase MCP 评估 §3.3）

- 面板每次打开、preset 每 10 秒窗口、每次写库 → 全量重扫 + 全量重写 index.json。当前量级无感，但正是「增量索引」建议的直接落点：为每篇文档记录 fs version 快照，refresh 时只重读变更文件、只更新其 grams；index.json 仅在变更集非空时重写。
- 写放大：每次写库重写整个 index.json。DESIGN 已定 >5000 篇按目录分片；建议把「增量写」作为阈值前的过渡手段一并列入。

### 3.4 设计文档与实际实现的出入（记录）

- `_meta/tags.json`（DESIGN §3.1）未实现——运行期从索引推导即可，建议从设计文档删除或标注「推导生成」。
- 配置面（DESIGN §4.9）大部分未落地：实际仅 archiveDir + trashRetentionDays；rootDir、search.topK/autoInject/bodyLimit、batchConfirmN、fetch 护栏、organize.maxDocsPerRun 等均为设计值。
- 变更事件流（§3.4）与 git 自动提交 hook（Phase 2）未实现——依赖 doc.created/updated/deleted/moved 事件，引擎目前无事件发布。

## 4. 优化建议清单

### P0 —— 一致性（建议近期实施）

1. **引擎服务化，消除双实现漂移**（§3.1，一揽子修复 #1–#7）。
2. 修 kb_update 重复 `updated:` 键（渲染前先设 meta.updated，或删除多余 push）。
3. 统一 images.json 为单一格式，host 的 imageTarget 与 resolve 读同一结构。
4. expectVersion 冲突：捕获 `FS_STALE_VERSION` 返回 `conflict: true`，或文档化异常语义并删除死字段。

### P1 —— 检索与索引（参考 codebase MCP 评估）

5. **相关度排序**：轻量词频 + 字段加权（title/aliases/tags > summary > body），pinned 置顶保留，时间仅作 tiebreak。
6. **字段语法进 GUI**：host search 支持 `tag:` / `path:` / `status:` / `title:` 过滤，与 preset 对齐并补齐 `title:`。
7. **单字符降级**：无 2-gram 时退化为线性子串扫描（中文单字可搜）。
8. **命中高亮**：search 结果携带命中片段或位置，面板高亮展示（需 wire 扩展）。
9. **增量索引**：fs version 快照 + 只重扫变更文件；面板打开改为快速 diff（§3.3）。
10. **批量操作确认门**：kb_import / kb_archive（非 dry-run）超过 N 篇（默认 5，可配置）先返回 dry-run 预览，用户确认后执行——kb_archive 已具备 dry-run，kb_import 补上。

### P2 —— 体验与远期

11. 自动引用注入 + 命中率/token 遥测（§4.3② / §4.10）：preset 提示词层加入「回答前先 kb_search」的检索预算与引用标注。
12. 剪藏护栏参数化：fetch 超时/重试/大小/SSRF 检查纳入配置。
13. index.json 增量写，>5000 篇阈值触发分片（§3.3）。
14. Phase 3 语义检索细化：按标题/段落/代码块分块（「代码片段」语料走 fenced code block 分块）、2-gram 与向量 RRF 融合、模型缺失/下载失败降级关键词（本地优先已规划）。
15. kb MCP server（反向方向）：harness 增加 mcp-server 能力后，把 kb 引擎包装为 MCP 服务，配合 Phase 3 常驻目标。

### 不采纳

- 不引入 codebase MCP 组件（[[2026-08-15-codebase-mcp-适用性评估]] 结论）。
- 不做 tags.json 静态化（运行期推导足够）。
- 不改「纯文件存储 + 路径推导状态」根基。
