# 知识库待定问题记录

本文档按时间记录知识库相关的待定问题与候选方向；有新问题直接追加小节。

## 1. 删除不释放磁盘字节

### 问题

回收站的「彻底删除」与自动清扫（超过 `trashRetentionDays` 的条目）都不会真正释放磁盘空间：条目只是从回收站列表消失，其字节仍留在磁盘上。

### 原因

fs 接口没有 delete/unlink 原语，文件只能被「就地置空」：文档写为单个空格，图片写为零字节。这是引擎与网关共同的底层限制，不是清除逻辑的疏忽。

### 现状行为

- 文档置空为 `' '`，图片置空为零字节；回收站列表跳过空文件，图片路由对零字节返回 404，用户界面上与「已删除」无差别。
- 磁盘占用不回收；被清除的文件在文件系统层面仍然存在，知识库目录的体积只会增长。
- `.trash` 目录里同样留下空文件占位。

### 候选方案（待定）

1. 给 fs 接口新增 delete/unlink 原语：最彻底，需要同时实现 fs-local 的物理删除、沙箱策略放行与 `fs/observed` 事件语义，属跨包改动。
2. 宿主侧定期扫描空文件并物理删除：不新增接口，但绕过沙箱语义，且需要区分「本就该为空的文件」与「置空标记」。
3. 记录置空清单（如 `_meta/purged.json`），由宿主在维护窗口统一删除：保留审计痕迹，但多一份需要同步的元数据。

### 决策

待定——先记录问题与候选方向，后续再决定如何处理。

## 2. 是否引入 codebase MCP

### 结论

不引入。评估见 [[2026-08-15-codebase-mcp-适用性评估]]：作为检索组件与知识库问题域不符且违背零依赖原则；仅借鉴其增量索引与混合检索模式（Phase 3），并可经 mcp-client 作为独立代码检索工具可选挂载。

## 3. 整体设计评估的待办方向

### 结论

整体评估见 [[2026-08-15-知识库整体设计评估与优化建议]]。待办按优先级：

- **P0（一致性）**：引擎服务化消除 host/preset 双实现漂移（01-inbox 与 archiveDir 状态不一致、images.json 格式冲突、kb_update 重复 updated 键、index.json 双写竞争等 7 处）；expectVersion 冲突字段为死代码。
- **P1（检索与索引）**：相关度排序、字段语法进 GUI、单字符降级、命中高亮、增量索引、批量操作确认门。
- **P2（体验与远期）**：自动引用注入与遥测、剪藏护栏参数化、index.json 增量写、Phase 3 分块与混合检索细化、kb MCP server 反向评估。

P0 的收敛方案已定（以 harness 设计理念为主）：保留 host 引擎并重塑为 `ctx.kb` 服务（Service 形态）、新增 `@deepseek-ai/dsh-tool-kb` 一等工具包、preset 收缩为纯组合行，见 [[2026-08-15-知识库双引擎收敛实施方案]]。
